# Requirement Extraction - QFC-1 Flight Controller

## 1. Initial Requirement (Vague Input)

The starting point of this system was a loosely defined requirement:

> "Build a flight controller. It should stabilize the drone and fly."

This requirement is insufficient for engineering because:

- No definition of "stabilize"
- No information about inputs/outputs
- No constraints (timing, hardware, safety)
- No system boundary

The goal of this document is to show how such a vague requirement was refined into a structured and testable specification.

## 2. Approach

Instead of attempting to design immediately, the requirement was refined through an iterative process:

Requirement -> Identify gaps -> Learn basics -> Ask questions -> Refine -> Repeat

The focus was to:

- Extract missing information
- Avoid assumptions
- Define clear system boundaries
- Introduce measurable behavior

## 3. Key Questions Asked

### 3.1 Purpose

- What is the system expected to do?
- Is the goal full flight or partial stabilization?
- What defines success?

**Decision:**  
System will stabilize roll and pitch only (bench validation).

### 3.2 System Boundary

- What is part of firmware vs external?
- Are we responsible for hardware configuration?
- Is this a full drone system?

**Decision:**  
Firmware is limited to control logic above HAL.  
Low-level drivers and hardware setup are out of scope.

### 3.3 Inputs and Outputs

- What data is available?
- What sensors are used?
- What outputs are required?

**Decision:**

- Input: IMU (accelerometer + gyroscope)
- Output: PWM signals to 4 motors

### 3.4 Timing and Real-Time Constraints

- How fast should the system react?
- Is deterministic timing required?

**Decision:**

- Control loop runs at 1 ms (1 kHz)
- All operations must complete within this window

### 3.5 Hardware Constraints

- Which platform is used?
- Any limitations?

**Decision:**

- Target: STM32-class MCU
- No dynamic memory allocation
- No RTOS

### 3.6 Interfaces

- How does firmware interact with hardware?
- Which communication protocols?

**Decision:**

- IMU via I2C
- PWM output via timer peripherals
- All access via HAL interface

### 3.7 Safety and Failure Handling

- What happens if something goes wrong?
- What is the safe state?

**Decision:**

- Define states: DISARMED, ARMED, FAULT
- Any fault forces system into FAULT
- Motors must be stopped in unsafe conditions

## 4. Key Assumptions

- System is stationary during calibration
- IMU provides valid data at required rate
- HAL functions are deterministic and reliable
- Bench testing only (no real flight conditions)

## 5. Iterative Refinement

### Iteration 1

- Basic idea: stabilize drone
- Missing: sensors, outputs, timing

### Iteration 2

- Added IMU input and motor outputs
- Still missing timing and safety

### Iteration 3

- Introduced 1 ms control loop
- Defined real-time constraint

### Iteration 4

- Added safety states (DISARMED, ARMED, FAULT)
- Defined fail-safe behavior

### Iteration 5

- Refined into structured functional and timing requirements

## 6. Result

The vague requirement was transformed into:

- Clearly defined system purpose
- Measurable functional requirements
- Deterministic timing constraints
- Defined safety behavior

These are captured in:

- `01-problem-statement.md`
- `02-requirements.md`

At this point, the system is better defined, but the work is still not complete. Requirements explain what the system must do, but they do not yet fully explain where the system begins and ends, what surrounds it, and which external actors interact with it.

That is why the next design step is system context.

## 7. Key Insight

Requirements are not given - they are engineered.

The process of asking the right questions and iterating is what converts ambiguity into a system that can actually be implemented.

## 8. Learning Outcome

- Do not wait for complete domain knowledge
- Start with partial understanding
- Refine continuously through questioning
- Maintain consistency while evolving requirements

This approach was critical in moving from a vague idea to a structured embedded system design.

## 9. What Comes Next

After requirement extraction, the next step is not implementation.

The next step is to define system context:

- What is inside the system boundary?
- What is outside it?
- Which actors interact with the system?
- What inputs and outputs cross that boundary?

Only after that does it make sense to move into use cases, functional responsibilities, and candidate modules or objects.
